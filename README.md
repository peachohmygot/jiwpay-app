# JiwPay · จิ๋วเปย์

React frontend ธีมน่ารักสีส้มจากดีไซน์เดิม พร้อมการ์ดปัดสลับ Visa เหรียญรางวัล เครื่องคิดเลข POS และเอฟเฟกต์ฉลอง ใช้ภาษาไทยเป็นหลัก รองรับมือถือและเดสก์ท็อป เชื่อมต่อ Google Apps Script ตาม payload ของโค้ดเดิม

## เริ่มใช้งาน

ใช้ Node.js 22.12+ และ pnpm หรือ npm:

```sh
npm install
npm run dev
```

- ลูกค้า: `http://localhost:5173/`
- ผู้ดูแล: `http://localhost:5173/#admin`
- `npm run build` สร้างไฟล์เผยแพร่ใน `dist/`
- `npm test` รันการทดสอบด้วย API จำลอง ไม่มีการส่งรายการเงินจริง

ใส่ URL `/exec` ใน `.env.local` ตามตัวอย่าง `.env.example` แล้วเริ่มเซิร์ฟเวอร์ใหม่ มี URL ที่คุณส่งมาเป็นค่าเริ่มต้นใน App.js และ Admin.js แล้ว **ห้ามใส่ Admin Key ในไฟล์ environment ฝั่ง frontend** ให้กรอกในหน้าล็อกอินผู้ดูแลเท่านั้น

หากใช้ pnpm: `pnpm install --frozen-lockfile`, `pnpm dev`, `pnpm build`, `pnpm test`

## สิ่งที่เปลี่ยน

- หน้ากระเป๋าเงินภาษาไทย ยอดเงินอ่านง่าย เมนูโอน/สแกน/เติมเงิน/กู้เงิน และแถบเมนูด้านล่าง
- กระปุกออมสิน บัตรเครดิต รับเงินผ่าน QR เครื่องรับชำระหน้าร้าน ประวัติรายการ และเหรียญรางวัล
- แดชบอร์ดผู้ดูแล รายการรออนุมัติ จัดการบัญชีและวงเงิน ค่าเช่า เหรียญ ประกาศ และเวลาเกม
- จำเซสชันด้วย `jiwpay_logged_account` / `jiwpay_admin_key` ไม่ล้างเซสชันเมื่อเครือข่ายหลุด
- แคชแยกตามบัญชี และแสดงข้อมูลที่ยืนยันแล้วทันที จากนั้นอัปเดตเบื้องหลังทุก 60 วินาที ขณะกลับมาใช้งาน/ออนไลน์ และเมื่อกดรีเฟรช
- ปรับยอด/สถานะบนหน้าจอทันที มี guard ด้วย ref ก่อน React render เพื่อป้องกันกดซ้ำ และปิดปุ่มระหว่างส่งรายการ
- คืน snapshot ทั้งชุดเมื่อรายการล้มเหลว ป้องกัน GET เก่าทับยอดใหม่ ไม่บันทึกยอด optimistic ที่ยังไม่ยืนยันลงแคช
- ไม่ retry POST อัตโนมัติเมื่อการเชื่อมต่อขาดหาย เพราะเซิร์ฟเวอร์อาจทำรายการสำเร็จไปแล้ว
- คำขอเงินกู้/เติมเงินแสดงเป็น “รออนุมัติ” ทันที แต่ไม่เพิ่มยอดเงินก่อนผู้ดูแลอนุมัติ
- อ่าน Topups / LoanRequests ด้วย `Users.id` และอ่าน Transactions ด้วยเลขบัญชี ตรงกับ GAS ที่ให้มา
- กล้อง mount video ก่อนขอ stream, มี playsInline/autoPlay/muted, หยุด tracks ตอนออกจากหน้า และรองรับ Strict Mode
- โหลด jsQR เมื่อเปิดสแกนเท่านั้น จำกัดความละเอียดที่ถอดรหัสและสแกนประมาณ 6–7 ครั้ง/วินาที
- QR ใช้ `encodeURIComponent` กับ JSON ทั้งชุด และมีทางกรอกบัญชีเมื่อเปิดกล้องไม่ได้
- รองรับ reduced motion, focus ของ dialog, ปุ่มปิดด้วย Escape, aria-label และสถานะโหลด

## ผลตรวจ URL จริง

วันที่ 22 กันยายน 2026 อ่าน `?sheet=GameState` สำเร็จ ได้:

```json
{ "ok": true, "sheet": "GameState", "scope": "self", "count": 0, "rows": [] }
```

อ่าน `?sheet=Badges` สำเร็จเช่นกัน และยังไม่มีเหรียญรางวัล (`rows: []`)

**ชีต GameState ว่าง เป็นสาเหตุที่ไม่มีเวลาแสดง** เข้าหน้าผู้ดูแล → เวลาในเกม → “ตั้งเวลาเริ่มต้น 06:00 น.” จะบันทึกวันที่ 1 เวลา 06:00 ให้ทั้งระบบ ยังไม่ได้กดตั้งค่าหรือส่ง POST ไปยังระบบจริงให้คุณ

โค้ด GAS ที่ให้มาไม่มีตัวเดินชั่วโมง/นาทีอัตโนมัติ: `runDailyRollover` เพิ่มเลขวัน และเมนูแอดมินปรับเวลาได้ Frontend จะแสดงเวลาจริงจาก backend ไม่สร้างนาฬิกาสมมติขึ้นเอง หากต้องการเร่งเวลาเกมตาม `timeScale` ต้องเพิ่มตรรกะเวลาใน backend

## ก่อนใช้งานจริง

Frontend สร้างและทดสอบได้ แต่ **ยังไม่ควรเรียกทั้งระบบว่า production-ready สำหรับเงินจริง** เพราะ GAS เดิมมีข้อจำกัดที่ React แก้แทนไม่ได้:

1. `login` คืนข้อมูลผู้ใช้ แต่ไม่ออก session token; `doGet` เชื่อ `userId` และ `transfer` เชื่อ `fromAccount` ที่ส่งมา การจำบัญชีใน localStorage เป็นเพียงการจำเซสชัน UI ไม่ใช่การยืนยันสิทธิ์บนเซิร์ฟเวอร์ ต้องตรวจ token/เจ้าของบัญชีทุก request และใช้การอนุญาตจากลูกค้าสำหรับ POS
2. `topup_decision` / `loan_decision` ไม่ตรวจว่าคำขอยัง pending และไม่ได้ล็อกการอนุมัติ จึงอนุมัติซ้ำจากหลายแท็บ/หลายผู้ดูแลได้ ต้องใช้ lock + ตรวจสถานะ + บันทึกผล request ID แบบ idempotent ฝั่ง GAS
3. เมื่อ POST timeout/เครือข่ายขาด ผลลัพธ์ไม่แน่นอน การ rollback บนหน้าจอไม่ได้ยกเลิกรายการที่ GAS อาจบันทึกแล้ว ต้องตรวจยอด/รายการล่าสุดก่อนส่งซ้ำ การรับประกันไม่ทำรายการซ้ำข้ามอุปกรณ์ต้องมี backend idempotency
4. ตรวจจำนวนเงิน, เจ้าของบัญชี, แผน/อัตราเงินกู้, วงเงิน, วันชำระ, QR version และข้อมูลอื่นที่ส่งจาก client บนเซิร์ฟเวอร์ บันทึกเงินแบบหน่วยย่อยหรือปัดเศษอย่างสม่ำเสมอ
5. `user_admin_upsert` เขียนยอดแบบ absolute จึงเสี่ยงทับธุรกรรมที่เกิดพร้อมกัน ต้องใช้คำสั่งปรับยอดแบบ delta ภายใต้ lock ฝั่ง GAS
6. ค่า Admin Key และข้อมูลแคชอยู่ใน localStorage ตามข้อกำหนด ควรใช้เฉพาะอุปกรณ์ที่เชื่อถือได้ และป้องกัน XSS; PIN ที่มีอยู่เป็นการล็อกหน้าจอในเครื่อง ไม่ใช่ขอบเขตความปลอดภัย

ไม่แก้หรือ deploy GAS ในงานนี้เพื่อหลีกเลี่ยงการเปลี่ยนกติกาการเงินของระบบโดยไม่ทดสอบร่วมกับ backend

## กล้องและการเผยแพร่

ใช้ HTTPS เมื่อเผยแพร่จริง และให้เว็บมีสิทธิ์ใช้กล้อง บางเวอร์ชันของ LINE/WebView อาจไม่อนุญาตกล้อง แม้ HTML ถูกต้องแล้ว ผู้ใช้สามารถเปิดผ่าน Safari/Chrome หรือกรอกบัญชีแทนได้ ทดสอบวงจรกล้องด้วย mock แล้ว แต่ยังไม่ได้ทดสอบกับอุปกรณ์ iPhone/LINE จริง

อัปโหลดไฟล์ใน `dist/` ไป static hosting ได้ ใช้ `/#admin` สำหรับแอดมินโดยไม่ต้องมี server rewrite เส้นทาง `/admin` ต้องให้โฮสต์ fallback มาที่ index.html

ยังไม่ได้สร้างหรือ push GitHub repository เพราะไม่มี repository ปลายทางที่ระบุ

## การตรวจสอบ

- Production build ด้วย Vite: ผ่าน
- Automated tests: ผ่าน 26/26 รวมการปิด–เปิดหน้าลูกค้าและแอดมินโดยไม่ล็อกอินซ้ำ
- Automated React tests: restore session, cache isolation, storage failure, optimistic loan/transfer/savings, duplicate clicks, rollback, stale GET protection, admin decisions, offline admin, manual refresh, empty game state, camera lifecycle ใน Strict Mode, และ QR encoding
- Browser layout checks: หน้าลูกค้าที่กว้าง 390px และแอดมินที่ 390px/1440px ด้วยข้อมูลจำลอง ตรวจ runtime error และ horizontal overflow
- รูปใน previews/ เป็นข้อมูลจำลองสำหรับตรวจ UI ไม่ใช่ยอดบัญชีจริง

เอกสารอ้างอิง: [React — effect cleanup และ race conditions](https://react.dev/reference/react/useEffect), [MDN — getUserMedia และ secure context](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

## พิมพ์ QR ติดบัตร

ผู้ดูแล → บัญชีผู้ใช้ → บัตร Visa / QR สำหรับให้ร้านค้าสแกน → พิมพ์ QR ติดบัตร เปิดหน้าพิมพ์แยกที่มี QR ความละเอียดสูงและชื่อเจ้าของ เลือกขนาดจริง 100% QR ไม่ผูกยอดเงิน ร้านค้าเป็นผู้ใส่ยอดและเลือกจ่ายเต็มหรือผ่อน 0% หลังสแกน การออกบัตรใหม่เพิ่มรุ่น QR; ต้องใช้ patch ใน `backend/CARD_QR_PATCH.md` และ deploy GAS เพื่อปฏิเสธ QR รุ่นเก่าที่ถูกแทนที่ ยังไม่ได้ deploy ให้

## สแกนจ่ายและสแกนรับเงิน

สแกนจ่ายเปิดกล้องอ่าน QR รับโอนของผู้รับ (action pay) แล้วแสดงชื่อและจำนวนเงินให้ตรวจสอบก่อนยืนยันโอนจากบัญชีผู้ใช้ ส่วนสแกนรับเงินใช้สำหรับร้านค้าสแกนบัตรลูกค้าเพื่อเรียกเก็บเงิน ไม่ใช้แทนกัน

เมนูสแกนรวมอยู่ในปุ่มเดียว มีแท็บสแกนจ่าย สแกนรับเงิน และ QR รับเงิน หน้าโอนมีรูป/ชื่อรายการโปรด ยอดด่วน 20/50/100 บาท และล็อกผู้รับที่มาจาก QR วงเงิน Visa ไม่อยู่ใน QR จึงไม่ต้องพิมพ์บัตรใหม่เมื่อคำนวณวงเงินใหม่

แบบพิมพ์บัตรกำหนดขนาดกว้าง 2 × สูง 3 นิ้ว (50.8 × 76.2 มม.) แนวตั้ง รวมขอบและระยะด้านในแล้ว พิมพ์ขนาดจริง 100% ปิดหัว/ท้ายกระดาษ และตัดตามขอบบัตร

ล่าสุด: สแกนรับเงินเปิดกล้องก่อน จากนั้นกรอกยอด เลือกจ่ายเต็ม/ผ่อน และแสดง dropdown 3/5 งวดเมื่อเลือกผ่อน ส่วน POS ใช้เครื่องคิดเลขสร้าง QR รับชำระ ดู DEPLOY-TH.md สำหรับขั้นตอนอัปเดต GitHub
